# Evans 1.0: a proposal

Status: **for Leon to decide.** Nothing here is agreed. Written 2026-11-11 from
`docs/ROADMAP.md` and the code, for the Phase 6 item "a stated stability policy,
and a 1.0 once Phases 1-2 land". Phases 0-4 are done, so that condition is met.

## What 1.0 would mean

1.0 says: *you can build on Evans without it breaking under you.* It is not a
claim that Evans does everything MATLAB does (the "Not in Evans" help page
says what it does not). It is a promise about what stays put.

## The stability policy

**1. Model files (`.evx`, `.fmdl`).**
- Any file Evans 1.x has written opens in every later 1.x. Any `.fmdl` written
  by 0.9 or later opens in every 1.x. Reading old files never gets dropped inside
  1.x.
- The file carries a format `version` (`sim/model.py`, `VERSION`). A change that
  older readers cannot understand raises it; a newer Evans refuses a file from a
  newer format with a message, never a silent misread. Additive changes (a new
  block type, a new optional field) do not raise it.
- `.fmdl` keeps opening for good. Only `.evx` is written by default; Save As
  keeps offering `.fmdl` for as long as the format version allows it.
- The `"format"` tag stays as it is.

**2. The console's MATLAB-compatible behaviour.**
- A script that gives MATLAB's answer in 1.x keeps giving it. A change that
  alters a result is a bug fix only when the old result differed from MATLAB's;
  those go in the changelog under *Changed* with the old and new answer (0.13.0
  did this for the Unit Delay).
- New commands and new options may appear in any 1.x. A command that is in the
  help index stays, with its argument order. Where Evans differs from MATLAB on
  purpose, the help page says so, and that difference is part of the promise too.
- Not promised: the exact wording of error messages and warnings, plot
  appearance (colours, fonts, layout), Python-side internals, and anything the
  "Not in Evans" page lists. The Python console features (`evans.*`) are
  best effort until the API is documented.

**3. Saved settings.**
- Settings written by any 1.x are read by every later 1.x. A renamed or removed
  key is migrated on first start, as the FauxMatlab one was. A setting that can no
  longer be honoured falls back to its default; it never stops Evans starting.
- Autosave recovery folders are not an archive: they are only promised to restore
  across a crash of the same version.

**4. Versioning after 1.0.** Semantic versioning, applied to the things above:
- **Patch (1.0.x):** fixes, including MATLAB-compatibility fixes, and new help.
- **Minor (1.x.0):** new commands, blocks, panes and file-format *additions*.
  Behaviour the policy promises does not change.
- **Major (2.0):** the only place a promise above may break, announced in the
  changelog's *Changed* section one minor release earlier where possible.
- Releases that are tagged but fail CI and never ship (0.12.0, 0.17.0) keep their
  changelog entry, marked as not released.

A short "Stability" section in the README and on the site would state this.

## Must-have before 1.0 (proposed)

| Item | Why it should block 1.0 |
|---|---|
| **The stability policy above, in the README and site, plus a `.evx` round-trip test** across every example and a fixture file per past format | A promise nobody can check is not one. The format version exists; what is missing is a test that keeps old files opening. Small. |
| **A reference corpus of real MATLAB outputs** (Phase 6; also closes the open "search for more silent wrong answers" item in Phase 0) | "MATLAB-compatible" is the promise. It is currently backed by closed-form tests and reading MATLAB's documentation. A corpus run once on a licence turns it into a regression suite. Medium; needs a MATLAB licence to produce. |
| **Numeric array writes in place** (Phase 0, `a(k) = v` is quadratic) | The one known performance trap in ordinary loops; 10^4 writes take 0.4 s and it grows with the square. A 1.0 user who pre-allocates and fills a vector should not hit it. Medium. |
| **A startup-time and size budget** (Phase 6) | Cheap, and stops 1.x from slowly getting heavier (343 MB today). Small. |
| **Mac update path** (read the `.dmg` asset; notarisation is a separate question, below) | Today a missing Windows asset hides the update from Macs. That is a bug, not a feature. Small. |

## Can wait until after 1.0

- **Handle graphics** (`h = plot(...)`, `set(h, ...)`): large, additive, no
  compatibility risk for existing files or scripts.
- **Better block shapes, scope overhaul, subsystem leftovers, script pre-run for
  a model, MIMO `linearize`, a user block API:** all additive. The script pre-run
  adds fields to the model file, which is allowed under the policy.
- **Phase 5** (serial hardware, system identification, `dsolve`) and **Phase 7**
  (acausal modelling, FMU, `.slx` import, code-first models, browser build,
  extensions): each is a large separate product decision. None changes what 1.0
  promises.
- **Profiler, `publish`, git status in the file browser, the `B905` audit.**
- **Self-updating on macOS:** needs notarisation first.

## Questions for you

1. **Code signing before 1.0?** The Windows installer is unsigned on purpose. A
   1.0 that SmartScreen warns about reads badly, but the Certum certificate costs
   money and the user count is small. Sign for 1.0, or keep it unsigned and say so
   in the release notes?
2. **macOS notarisation before 1.0?** The Apple developer fee, and it is the
   prerequisite for Mac self-update. Is a Mac-first-launch warning acceptable at
   1.0? And an Intel build: only if someone asks?
3. **A Linux build (AppImage or `.deb`)?** CI already tests on Ubuntu. Is Linux a
   1.0 platform, or "runs from source" until later? The policy above would then
   name the platforms it covers.
4. **Does the reference corpus block 1.0?** It needs a MATLAB licence, which only
   you may have access to. If not, the MATLAB-compatibility promise is worded
   more softly ("where documented").
5. **How long do you guarantee `.fmdl` reading?** The proposal says all of 1.x.
   A shorter promise is cheaper to keep.
6. **Is the Python-side API (`evans.*`) part of the promise,** or console-only?
   The proposal leaves it out.
7. **Date or readiness?** 1.0 when the must-haves land, or on a date (a semester
   start, say) with whatever has landed?
